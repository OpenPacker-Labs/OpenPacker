# ADR 0048: One copy of a package per machine, and a node_modules Node can resolve

- Status: Accepted
- Date: 2026-10-11
- Amends [ADR 0034](0034-opm-projects-into-native-project-formats.md) (the
  `layout` level) and [ADR 0042](0042-upm-v1-gaps.md) §3 ("Optional shared blob
  CAS … No toml schema key")
- Amended by [ADR 0050](0050-workspace-member-links.md): the no-symlink rule has
  one exception, a workspace member's link (decided 2026-10-12, see
  [Amendment](#amendment-2026-10-12-workspace-member-links))
- Extended by [ADR 0051](0051-opm-ci-installs-workspace-locks.md): a workspace
  member has a `node_modules` of its own beside its source, laid out and
  recorded by these rules
- Amended 2026-10-17: an install's claims, not the ten-minute grace, keep
  `opm gc --shared` from an entry the install is using (see
  [Amendment](#amendment-2026-10-17-an-installs-claims-keep-opm-gc---shared-away))

## Context

Installing 50 packages (79 MB unpacked, offline: the file counts, directory
counts and file sizes of 50 real packages from this repository's `node_modules`,
with a lock in which six names have two versions) cost this much before this
change, in MiB by `du -sk` over every path at once, so a hard-linked inode
counts once:

| Setup                                        | First project | A second project |
| -------------------------------------------- | ------------: | ---------------: |
| Project-local store, `node_modules` written  |     171.1 MiB |       +171.1 MiB |
| `OPM_STORE_HOME` set (the only way to share) |     223.6 MiB |        +90.9 MiB |

and the `node_modules` it wrote kept one version of each name, silently dropping
six of the 50 packages the lock selected. Four separate faults caused it:

1. A package was stored three times. The extracted tree, a gzip copy of the
   tarball beside it (`.opm/store/<key>.artifact`, kept for offline repair), and
   a byte-for-byte copy in `node_modules`: `materialiseTree` documented a
   hardlink and always copied. With `OPM_STORE_HOME` set the shared root kept
   its own tarball too, and each project still wrote its own.
2. Nothing shared by default. The shared store (ADR 0042 §3) was an environment
   variable nobody sets, so every project and every worktree held every package.
3. `native_projection = "layout"` wrote nothing in a project without a
   `package.json`: every projection began with `format.detect()`, which knows a
   project only by its manifest.
4. The layout was flat. Node resolves `require('c')` from the nearest
   `node_modules` up the tree, so `a → c@1` and `b → c@2` cannot both be right
   in a flat directory.

Making the store the default also exposed three faults that the opt-in had
hidden: the shared store refused any file name beyond `[A-Za-z0-9._-]` (so a
package shipping `[id].js` or `+page.svelte` could not be installed), two
installs publishing the same package at once failed, and hashing a tree failed
whenever another project linked one of its files at that moment.

## Decision

### `layout` needs no manifest, and Node can resolve what it writes

1. At the `layout` level an adapter that offers `detectLayout()` writes its
   layout from the lock and the store alone. For npm that is `node_modules`,
   with or without a `package.json`. opm creates no manifest and no lockfile the
   person did not ask for, and says so in the projection's loss. `manifest` and
   `lock` keep requiring the native file, as in ADR 0034. The default level is
   still `manifest`.
2. The tree is planned from the dependency edges the lock records (`alias` and
   `dependencies` on `NativeLockEntry`), not from names. A direct requirement,
   and the version of a name that most packages want, live at the root; any
   other version is nested in its dependent's own `node_modules`. Each package
   is judged from where it really lives, so a nested copy that shadows the root
   is respected. A lock with no edges (an offline lock holds only the direct
   set) still lays out flat by name, newest first, and reports the loser instead
   of overwriting it. No symlinks, except a workspace member's link
   ([Amendment](#amendment-2026-10-12-workspace-member-links)).
3. Executables are POSIX shell shims in `node_modules/.bin` (and `.cmd` on
   Windows) that run the package's script with the interpreter its shebang asks
   for, addressed relative to the shim. Names and targets from `package.json`
   are validated, not escaped. Lifecycle scripts stay off.
4. `node_modules/.opm-layout.json` lists what opm wrote, so the next layout
   removes only that (ADR 0034 §4): removing the last package clears the layout,
   and a package someone installed by hand is never touched.

### Packages exist once on disk

5. Files are hard links, verified. `materialiseTree` gains `link`: each file is
   linked through the open directory handles and the new name must be the very
   inode that was opened and inspected, or it is removed and the layout fails
   closed. A filesystem that cannot link falls back to the verified copy, and
   the projection says "copied". A linked inode keeps the store's mode and is
   never changed from the project side.
6. A user-level shared store is the default for the `opm` and `opmx` process
   entries: `$XDG_CACHE_HOME/openpacker/store`, else
   `~/.cache/openpacker/store`, beside the `opmx` tool cache. It stays
   **environment-only with no toml key**: a committed `opm.toml` must not decide
   where a machine keeps its packages, or point a teammate's store somewhere
   else. `OPM_STORE_HOME=/abs/path` relocates it, `OPM_STORE_HOME=off` opts out
   (blank means unset, a relative path is `UNSAFE_PATH`). The library functions
   never enable it themselves, so tests and embedding hosts do not write to the
   user cache.
7. It is only used where it saves disk and is safe:
   - Created `0700`, owned by the current user, never group- or world-writable.
     An entry's recorded tree digest catches corruption, not tampering, so
     nobody else may write the root. An explicit `OPM_STORE_HOME` that fails the
     check is an error; the default falls back to a project-local store and
     never makes an install fail.
   - The default is used only when it is on the project's filesystem. Across
     devices every link would become a copy and the store would only add a
     second one. An explicit root is used as named.
   - Entry files are read-only, so the in-place edit that would corrupt every
     project fails instead of succeeding, and adoption re-hashes the entry and
     the project's linked tree, so one that was changed anyway is found before
     it is trusted. A package whose lifecycle scripts run first gets private,
     writable copies.
   - No tarball is kept where the tree is shared. The shared tree is the cache;
     a lost entry is rebuilt from the lock's source or the registry and
     re-verified against the lock's digest. A project-local store (opt-out)
     keeps its `.artifact` for offline repair, as before.
   - Two installs publishing one package adopt one result; an install that races
     a collection publishes again; a tree being hashed while another project
     links it is not mistaken for a changing tree (`linkTolerant`, default off).
   - A package may ship any name that is a single path segment. The materializer
     already refused traversal, absolute paths, Windows device names and links.
8. `opm gc --shared [--dry-run]` removes entries no project links to: a
   project's store entry and its `node_modules` are links to an entry's files,
   so an entry in which every file has a link count of one is held by nothing
   but the shared root. It needs no project, leaves entries younger than ten
   minutes alone (an install may be about to link them), and clears half-written
   temporaries. Project `gc` never touches the shared root.

## Consequences

Measured the same way, on the same fixture (all 50 packages installed, every
dependency edge checked by a real Node `require.resolve` from the dependent's
directory):

| Setup                                        | First project | A second project |
| -------------------------------------------- | ------------: | ---------------: |
| `OPM_STORE_HOME=off`, `node_modules` written |     133.9 MiB |       +133.9 MiB |
| Default shared store                         |      84.2 MiB | +2.6 MiB (3.09%) |

A third worktree adds 2.6 MiB again. Per project that is directories (the store
entry's tree and `node_modules`, a block each), one `links/*.json` per package
and the lock. The pnpm figure given for a different 48-package closure is 74 MB
cold and about 1 MB for a second project (about 1.4%); this fixture is not that
closure, so the comparison that holds is the ratio, 3.1% against about 1.4%. The
gap is the second directory tree (`.opm/store`) every project keeps beside
`node_modules`.

Costs and limits, stated so nobody finds them by surprise:

- Hard links share an inode, so an in-place edit of a file under `node_modules`
  fails (it is read-only) instead of changing every project. Tools that replace
  a file by writing a new one and renaming it are unaffected; `chmod u+w` then
  write works and is caught by the next adoption's digest check, which names the
  entry to remove.
- Windows has no handle-relative link here, so the layout is copied there and
  the default store is off.
- A filesystem that supports reflinks would give copy-on-write isolation with no
  shared inode; it is not used yet.
- Offline repair of a lost shared entry needs the source or the registry; an
  opt-out project keeps its tarball.
- The shared root is not size-bounded; `opm gc --shared` is explicit.
- The placement is correct for the selected versions, not necessarily the one
  npm would choose (it does not hoist a nested package above its dependent), and
  peer dependencies are placed only as far as the lock recorded them.

Not changed: the default projection level, `.opm/store` as the activation tree
and its generations, the supply-chain gates, and `blockExoticSources`.

## Amendment (2026-10-12): workspace-member links

The rule that `node_modules` has no symlinks, so that a path inside it is never
an alias for a path outside it, has one exception. The user decided on
2026-10-12 that **symlinks (junctions on Windows) are allowed for
workspace-member links only, created through the no-follow handle API and
refused everywhere else.** A workspace repository needs a member's name in
`node_modules` to resolve the member's live source.

The rule now reads: nothing in `node_modules` is a symlink except a link from a
workspace member's name to the member's own directory, declared in the layout
plan, written by the layout writer through `symlinkChild`, and listed in
`.opm-layout.json`. Not a registry package, not a bin (`.bin` stays script
shims), not a nested copy. Reading and removing still never follow a link: a
walker refuses a link the record does not name, `materialiseTree` refuses a
source tree that holds one, and removal unlinks without entering it.

What a link is, how each platform makes it (including the Windows junction and
the one window that remains there), and how the plan, the writer and the record
carry it are in [ADR 0050](0050-workspace-member-links.md).

## Amendment (2026-10-17): an install's claims keep `opm gc --shared` away

### Problem

§8 left an entry younger than ten minutes alone because "an install may be about
to link" it. That covered an entry an install had just published, by timing, and
nothing else. An install that _adopts_ an entry (finds it in the store) and
links it later leaves it linked by nobody in between, and an adopted entry is as
old as its first publication. `opm ci` keeps every entry in that state from the
moment it is found until `node_modules` is written, and clears `node_modules`
first, so for a whole install. A collection in that window removed the entry:
`opm ci` then failed with `UNSAFE_PATH` ("Layout path is linked, special, or
unstable", naming the vanished entry), and `opm install` retried by publishing
again, which needs the archive and so fails offline. Measured with a
deterministic test (the collection run between "in the store" and "linked",
`minimumAgeMs: 0`): 30 of 30 runs failed before this amendment.

### Decision

An install **claims** each entry before it decides whether the store has it, and
keeps the claims until its links are published; a collection **announces** each
entry before it decides on it, and leaves one that is claimed. Both write before
they read:

- install: append the entry's key to its lease; wait while a live collection has
  announced that key and not settled it; then look the entry up, publish it if
  need be, and link it;
- collection: append `+key` to its own lease; leave the entry if a live install
  has claimed it, or if anything links it by now; otherwise unpublish it
  (rename, then its records) and append `-key`.

If the collection does not see a claim, the claim was written after the
collection started looking, so the install's own look comes after the
announcement and waits until the entry is gone, then publishes it again. If it
sees the claim it leaves the entry. So no install links an entry a collection
removes, and an entry an install has decided to use stays until its links hold
it. Installs never wait for each other (a claim is shared), a collection never
waits for an install (it leaves the entry), and an install waits for a
collection only while it decides on and settles one entry: it reads the
installs' leases, looks through the entry's tree for a second link, renames the
entry away and removes two records, and never fetches. An install waits on one
announcement for 45 seconds at most (`ANNOUNCEMENT_WAIT_MS`): one still open
after that was most likely left by a collection that died where this process
cannot judge it (another machine, another pid namespace), and the install says
so, naming that collection's lease, and goes on. Going on is safe: a collection
unpublishes an entry by one rename, `opm ci` looks at every entry it linked from
once its layout is written (below), and `opm install` publishes again an entry
that vanished. An install that is cancelled stops waiting. `opm ci` holds the
store from its first lookup to its last link; `opm install`, `add` and `update`
hold it across the closure, and each package claims its own entry.

A lease (`<store>/.leases/<id>.lock` and `<id>.keys`) is tied to a live process,
so a holder that is killed stops counting at once:

| Platform    | A lock is held while                                       |
| ----------- | ---------------------------------------------------------- |
| Linux       | `/proc/<pid>/fd` has a descriptor on the lock file's inode |
| macOS, BSDs | it is `flock`ed (`O_EXLOCK` at open)                       |
| Windows     | it is open with no sharing (libuv's `UV_FS_O_EXLOCK`)      |
| otherwise   | the pid is running                                         |

Each mechanism is checked when the lease is made; where it does not hold (or a
filesystem refuses `O_EXLOCK` as unsupported), the lease falls back to the pid.
The operating system closes a dead process's descriptors and drops its locks, so
the first three do not outlive their holder; a reused pid can keep a fallback
lease alive until that process ends, which delays a collection and never removes
anything wrongly. A lease's name also says who holds it and where: the pid, its
start time (Linux), the pid namespace, the machine's boot (the kernel's boot id)
and the machine (`/etc/machine-id`, or a digest of the host name where there is
none, and a digest of the host name); a `pid` lease whose pid now belongs to a
process that started later is abandoned, and so is a lease whose machine id and
host name are this machine's and whose boot is not this one, since its holder
ended with that boot. A `proc` lease whose pid is now a process whose
descriptors the reader may not list (another user's, one that is not dumpable)
is judged as a `pid` lease is, by whether that process started when the holder
did: `/proc/<pid>/stat` is readable by anyone, and without it a dead holder's
lease would stay for as long as its pid does. A start time that cannot be read,
or that the lease does not record, counts as held. Every other check errs
towards "held": a lease made on another machine (a store several hosts share),
in a boot it cannot place (this machine id under another host name, as a cloned
machine would have), or in another pid namespace (a container sharing the store)
counts as held, because nothing here can judge that process, and so does one in
this namespace when this process cannot read it. The owner and this rule are one
small module (`lease-owner.ts`). A lock is held before it is renamed from
`<id>.pending` to `<id>.lock`, a reader looks for the `.pending` name before the
`.lock` one, and a lease's keys go before its lock: so a reader never mistakes a
lease being made or released for an abandoned one. (Looking for `.lock` first
missed a lock renamed between the two looks, and a collection starting up then
removed a live install's lease.) The last lease out removes `.leases`; a
collection removes the leases of holders that are gone. Leases written under the
two names earlier builds of this change used are not read, so they neither
protect an entry nor expose one; a collection removes their files once they are
a day old, so they do not keep `.leases` from being removed. A name of no format
this build knows is left alone, however old: it may be a newer build's lease.

As a backstop for removers that do not claim (an older opm's collection, a
person removing entries whole), `opm ci` looks at every entry it linked from
once `node_modules` is written. An entry whose directory vanished is fetched
again, checked against the lock, published, and the layout written again, once;
one still missing after that, or that cannot be fetched, fails with
`STORE_ENTRY_VANISHED` naming the entry and the packages from it, and one whose
bytes fetched again are not what the lock pins fails as that verification
failure. The check is that each entry's directory is there: an entry a person
removed part of (some files, the directory left) is not caught by it. A
collection unpublishes an entry whole, by one rename. `opm install` publishes a
vanished entry again once, as before, and then fails with the same code. The
ten-minute grace stays, for older opm versions that do not claim; correctness no
longer rests on it.

The worst case of going on after the 45 seconds: an install that gave up waiting
on a live collection publishes the entry in the few milliseconds between the
collection's rename of it and its removal of the entry's `.tree` record. The
collection then removes the new record, and the entry stays without its tree
digest; the next install that adopts it fails with `VERIFICATION_FAILED`
("Shared store entry is missing its tree digest"), and the message names the
entry to remove before running the command again. It needs a collection that
stays open on one entry for over 45 seconds and an install arriving in that
window.

### Consequences

- 30 of 30 runs of the race test pass; a collection between two concurrent
  installs, each held between "in the store" and "linked", removes nothing, and
  a holder killed with `SIGKILL` no longer holds its entry for the next
  collection.
- Verified on Linux only. The macOS (`O_EXLOCK`) and Windows (no sharing)
  mechanisms are written to their platforms' documented behaviour and checked
  when each lease is made, falling back to the pid when they do not hold; they
  have not been run here.
- A collection that is stopped (not killed) in the middle of settling an entry,
  or that died where this process cannot judge it, makes an install that wants
  that entry wait 45 seconds, after which it warns and goes on.
- `.leases` costs a lease per install: on this machine (load average about 40 on
  4 CPUs) about 3 ms to take and release, and 0.1 to 1 ms per claim however long
  a running collection's lease has grown, since a hold reads each collection's
  lease once, from where it stopped (it was 43 ms per claim against a lease of
  20 000 settled entries when every claim read it from the start).
- A store on a filesystem several machines share keeps each machine's claims
  from the others' collections, since another machine's lease counts as held.
  The cost of erring towards "held": a lease left by a holder that died on
  another machine is removed only by a collection on that machine, and one left
  in a container that is gone only by hand, from `<store>/.leases/`; until then
  it keeps the entries it claimed. A lease left by a boot of this machine that
  has ended (a crash, a power cut) is removed by the next collection.
- Sharing the store over a network filesystem is not supported: nothing here was
  run against one, and hard links, `O_EXLOCK` and an atomic rename are what such
  filesystems vary in. Where one is used anyway, the lease names above err
  towards "held", with one exception. Machines with the same `/etc/machine-id`
  and the same host name (an image cloned as it was) cannot be told apart, so a
  collection on one reads the other's live leases, made in a boot with another
  boot id, as those of an ended boot of its own machine, and removes them. Give
  every machine its own machine id and host name, or its own store.
- An install that would only adopt still needs its lease. A full disk (`ENOSPC`,
  `EDQUOT`) while the lease is made fails the install with that error, where
  before leases it would have adopted what the store holds. Only a store the
  install may not write (`EROFS`, `EACCES`, `EPERM`) is adopted from without a
  lease: a store with no room for a lock file is not one in which an install can
  put its claims where a collection will see them.
- An install against a store it may read and not write (a read-only mount, a
  root of mode `0500`) takes no lease there: its lease is opened by its first
  claim, and one the store refuses (`EROFS`, `EACCES`, `EPERM`) leaves it
  adopting what the store holds and writing nothing, as before leases. It still
  waits on the collections it can see, and `opm ci` still looks at every entry
  it linked from once `node_modules` is written. Its entries are not claimed, so
  a collection run by someone who can write the store may remove one meanwhile;
  `opm ci` then fails with `STORE_ENTRY_VANISHED` naming it, since nothing in
  that install can put the entry back.
